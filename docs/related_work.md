# Related Work: PHLAME Next to Other TinyML Benchmarks and Tools

This page covers the works listed under [References](#references); it is not a systematic survey. A section number in brackets says where in a source a statement is found.

## What the Other Benchmarks and Tools Measure

**MLPerf Tiny** [1], which its authors present as an industry-standard suite, compares hardware and software stacks under run rules with a closed and an open division, on four tasks [1, §4–5] and, since v1.3, a streaming wake-word test [2]. Its harness sends input files from a host to the device over a serial port, with no physical sensor in the loop, and reports accuracy, throughput and, in a second and optional configuration, energy per inference [1, §5.3 and Appendix A; 3; 5]. The results repository prescribes, for each system and benchmark, the runner log of the accuracy run [4]; the log cited there holds the output vector of the device for each of its 1,000 input files. The paper gives the accuracy of its float and quantized reference models where it sets the quality targets [1, §4], as aggregates; we found no host output per input to compare the device with.

**Benchmarking tools** compare frameworks, compilers and boards on latency and memory. MLonMCU [6] does it for deployment flows, on an instruction-set simulator and on four boards [6, §III]. EdgeMark [7] also measures a deployment error: the mean normalised difference between the output on the device and the output of the unoptimised model on a PC, over ten inputs [7, §4]. MLino Bench [8] sends test vectors over serial and reports on-target accuracy, classification time and model size (README); its repository code collects the class returned for each vector to compute that accuracy and does not store it, and can log the accuracy of the desktop model as well. U-TOE [26] measures memory, storage and latency per model and per operator on boards, with random inputs and no accuracy [26, §IV].

**Energy.** CREST [10] measures latency and energy on boards, the Portenta H7 among them, while it selects models, and computes task quality on the host [10, §5–6]. Bartoli et al. [11] measure energy and latency per phase on the four MLPerf Tiny models; the firmware sends each prediction to the PC so that accuracy can be computed, but the paper reports no accuracy figures [11, §IV–V].

**Vendor tools** check the deployed model against the original one. The `validate` command of ST Edge AI Core [12, 13] runs the original model with its own inference engine on the host, and the generated C model on the host or, over a serial link, on the target; it saves the inputs and outputs of both, computes error metrics and, for classifiers, the accuracy and a confusion matrix of one against the other, and times each layer on the device. Its documentation expects a small representative subset of the data, not a whole test set. Edge Impulse [14–16] tests the float32 or the int8 variant of a model on the test set in its Studio, sample by sample [15], estimates latency from Renode and device benchmarks [14, §4.4], and runs the deployed model on the board on live sensor data, where there are no labelled stimuli [16]. MathWorks documents a deep-learning network running on a Cortex-M board in processor-in-the-loop mode, with its output compared with that of MATLAB within a tolerance and with execution profiling [17]: PIL for neural networks did not start with PHLAME. MIL, SIL and PIL are terms of model-based design; [17] uses only PIL.

**Deployment validation on phones.** ML-EXray [29], which [26] cites, instruments an application on a phone, logs the output of the model and of each layer, replays the same data through a reference pipeline on a workstation and compares accuracy and per-layer error on standard public datasets (the paper names ImageNet, COCO and Speech Commands); one of its comparisons is the same quantized model run with the optimized and with the reference kernels of TFLite [29, §3–4]. Its devices are two Pixel phones, not microcontrollers.

The table adds the functional simulators [18–21] and PICO [9], which runs on two Cortex-A boards, not on microcontrollers. Kenning [27] runs and evaluates models on target devices and stores predictions and ground truth in its measurement files; it is not compared further here.

## What PHLAME Adds

1. **The same test images at every level, every prediction published, paired statistics.** MIL, SIL and PIL are evaluated on the complete test set and the camera level (HIL) on a fixed subset of it. Every level stores the prediction of each image, in the repository, and the levels are compared image by image: agreement counts and, with the four levels measured, exact McNemar tests with Holm correction and paired bootstrap intervals. To our knowledge, none of the systems reviewed publishes the predictions of the host and of a microcontroller for a complete test set and compares them with paired statistical tests. Parts of it exist elsewhere. The MLPerf Tiny results repository holds, per system, the log of the accuracy run, and the log cited has the output of the device for every input, with no host output beside it [4]. ST saves the outputs of the original model and of the C model and reports the agreement between them, on the small subset its documentation expects and as plain metrics, with no statistical test [12]. EdgeMark reports a mean output error over ten inputs [7]. ML-EXray logs and compares the device and a reference pipeline on public datasets, on phones and as accuracy and per-layer error [29]. Edge Impulse keeps, in its Studio, the result of each test sample for the float32 and the int8 variant [15]. Kenning stores predictions and ground truth in its measurement files [27].
2. **The camera in front of labelled stimuli.** At the HIL level the camera of the board looks at a monitor that shows each test image, so every captured frame has a label, and classifying the same frames on the PC separates the effect of the camera from that of the chip. To our knowledge, no benchmark among the sources reviewed puts the physical sensor of a microcontroller board in front of labelled stimuli; the review was not a systematic search. The others replace or bypass the sensor: MLPerf Tiny sends files over UART and, in its streaming test, stored audio over I2S [3]; Bartoli et al. load each input from flash [11]; CREST leaves sensor acquisition outside its measurement [10, §6]; ML-EXray reads its data from storage instead of the sensor [29, §4]; Renode feeds recorded data to a simulated sensor [21]. Edge Impulse does use the sensor of the device, to collect the samples of its labelled datasets, which the Studio then classifies, and to run the deployed model on live data [14–16]; it does not replay a labelled test set in front of the sensor. The closest precedent we know is outside TinyML: Kurakin et al. print clean and adversarial ImageNet images, photograph the pages with a phone camera and compare the accuracy of an Inception classifier before and after that step [25, §3].
3. **The measured difference between the PC interpreter and the chip.** On the 5,000 COCO test images, for four of the five models that fit the board, the default TFLite interpreter (XNNPACK delegate) gives another prediction than the chip for 27 to 80 images, and the reference kernels of TFLite for 1 to 25 (for the fifth model see [`coco_benchmark.md`](coco_benchmark.md#notes-on-the-results)). That integer kernels on a PC and on a microcontroller can disagree is known to TFLM developers: the CMSIS-NN README states bit-exactness with the reference kernels of TFLite and adds that the reference kernels of TFLite and of TFLM are not always bit-exact with each other [22]; an open TFLM issue attributes output mismatches to the two rounding schemes of requantization and gives an off-by-one rate of about 1.8% for that operation [23]; and a user of the TFLM mailing list reported predictions on an Arduino Nano 33 BLE Sense that differed from those of the TFLite interpreter, without figures [24]. The difference has also been measured in other settings: ML-EXray compares, on phones and on image-classification data, the top-1 accuracy and the per-layer error of the same quantized model with optimized and with reference kernels [29, §4.4]; EdgeMark reports the mean output error of the board against the unoptimised model on a PC, over ten inputs [7]; and the `validate` command of ST computes the agreement between the TFLite interpreter and its C model, on the host or on the target, for the data the user supplies, with an example of 128 samples on the host in its documentation [12]. What the sources reviewed do not give is the count, for a microcontroller and over the test set of a public benchmark, of the images on which the PC interpreter and the chip predict differently. The chip runs CMSIS-NN kernels for most operators of these models ([`hardware.md`](hardware.md#boards-and-memory)), so the figures check on hardware the bit-exactness that the CMSIS-NN README states [22].

## What PHLAME Does Not Do

- **No energy.** Neither energy nor power is measured. MLPerf Tiny, CREST and Bartoli et al. measure it.
- **One microcontroller, one runtime.** Both boards carry the same STM32H747 and run TFLM through the same library, so their identical predictions are a consistency check, not a portability result.
- **One kind of task.** Binary classification of 160×120 grayscale images. Its COCO figures are not comparable with those of the visual wake words task of MLPerf Tiny: 96×96 colour input, another reference model, other rules [1, §4.1; 4].
- **No standardised submission process.** No run rules, divisions, review of submitted results or community of submitters, and one maintainer. PHLAME is not a ranking of hardware.
- **No release yet.** No tagged release and no DOI.
- **Less than the vendor tools in two respects.** The firmware returns only the predicted class, so metrics over the output vector, which ST and MLPerf Tiny compute [12; 1, §5.3], cannot be obtained from a board run. And its SIL runs TFLite on the PC, not the kernels of the firmware. ST compiles its generated C model for the host as well [12, 13], and TFLM itself can be run on the host through its Python package [28]; the README of that package does not say which kernel implementations the build uses, and marks part of itself as under construction.
- **Per-phase latency is not specific to it.** Bartoli et al., ST and Edge Impulse also time phases, layers or stages, and U-TOE and ML-EXray time operators or layers.
- **Also:** post-training quantization only, published PIL files that predate the on-chip check of the model, and PIL runs of 65 minutes to almost 5 hours for 5,000 images at 115,200 baud.

The levels measured on the public benchmark are stated in the README ([Results](../README.md#results), section 1), and the limitations of the framework under [Known Limitations](../README.md#known-limitations).
